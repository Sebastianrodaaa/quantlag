# quantlag: does unbiased export fix the lag of quantized CPU rollouts?

Small-scale CPU study. Every number below comes from `results/*.json`, produced on one
8-core Intel Xeon (AVX2, no GPU) by the code in this repository. Tables are regenerated by
`python3 scripts/plots.py` into `results/summary.md`.

## Question

RL post-training keeps fp32 master weights in the optimizer and samples rollouts from a
cheaper served copy. On CPU that copy is int8 or int4. If the served copy is re-made from the
master with round-to-nearest (RTN), a per-step update smaller than half a grid step is
discarded, so the policy that generates the data can lag the optimizer. Fair Cast showed this
for bf16 on GPU and fixed it with an unbiased export (stochastic rounding or error feedback)
plus computing the loss on the served copy. QuRL attacked the same "weight update problem"
for int8/fp8 with invariant scaling.

Hypothesis (from the brief): with RTN, under 1% of served weights change per step after the
first steps; error feedback (EF) tracks the master more closely and, if lag matters, improves
GSM8K accuracy after a fixed number of GRPO steps. If it does not, say so.

## Method

### Grids (`quantlag/export.py`)

- `bf16`: round fp32 to bfloat16.
- `int8`: symmetric, one scale per output channel, `scale = absmax / 127`.
- `int4`: symmetric, groups of 32 along the input dimension, `scale = absmax / 7`.

Integer scales are computed once from the initial weights and then frozen, as in a deployed
quantized copy that is patched in place. Only the 2-D linear weights inside the transformer
blocks are quantized; embeddings, norms and the LM head stay full precision.

### Export rules

All rules start from the same RTN snapshot `q0` of the initial master `w0`.

| rule | served copy after a master update `d = w_t - w_(t-1)` |
|---|---|
| `rtn` | `Q_rtn(w_t)`: re-quantize the master (the usual export) |
| `sr` | `Q_sr(served + d)`: stochastic rounding of the update onto the grid, `E[served_t] = q0 + (w_t - w0)` |
| `ef` | `Q_rtn(served + d + r)`, residual `r` keeps what did not fit, `abs(r) <= half a step` |
| `qurl` | invariant scaling (below), then `rtn` |

For bf16, `w0` is already on the grid (checkpoints are bf16), so `q0 = w0` and `sr`/`ef` are
exactly Fair Cast's stochastic-rounding and error-feedback exports. For int8/int4 `w0` is not
on the grid; re-rounding the whole master stochastically would add a fresh half-step of noise
to every weight at every sync (we measured a third of all int8 codes flipping per sync with
that variant before switching), so the unbiased rules here round the update, not the weight.

QuRL invariant scaling is implemented as a one-time reparameterization: in every block the
two RMSNorm weights are multiplied by `s = 1.5` and the q/k/v/gate/up projections that read
them are divided by `s`. The function is unchanged in exact arithmetic, the quantized weights
shrink relative to their per-channel absmax only where the norm scale is not the absmax, and
AdamW updates (scale-free) become relatively larger in grid units. This is our reading of the
paper's invariant scaling, not the authors' code, and Adaptive Clipping Range is not
implemented.

### Phase 1: replay (`quantlag/lag.py`)

Real AdamW updates (`betas = (0.9, 0.99)`, no weight decay) from supervised fine-tuning on
GSM8K train answers (batch 8, up to 320 tokens, 50 steps), at learning rates 1e-6, 3e-6 and
1e-5, on SmolLM2-135M-Instruct and Qwen2.5-0.5B-Instruct. The master trains on its own loss;
every export rule watches the same master trajectory. Per step we log:

- `changed_frac`: share of quantized weights whose served code changed at this sync,
- `realized`: `<served_t - q0, w_t - w0> / |w_t - w0|^2`, 1 means the served copy moved by the
  full cumulative update, 0 means it did not move,
- `track_err`: `|(served_t - q0) - (w_t - w0)| / |w_t - w0|`.

At fixed steps we compute token-level `KL(master || served)` on the response tokens of the
last 100 GSM8K test problems with their reference solutions, plus `stuck`, the KL to a copy
whose block weights never leave step 0 (the worst case of lag).

### Phase 2: GRPO (`quantlag/grpo.py`)

Qwen2.5-0.5B-Instruct, GSM8K train, 8 prompts x 4 samples per step, temperature 1, up to 256
new tokens, reward 1 if the last `\boxed{}` (or last number) equals the reference answer.
Group-normalized advantages, sequence-mean log-prob loss, AdamW lr 1e-5, gradient clip 1.0.
Rollouts are sampled from the served int8 copy and the loss is computed on the same served
weights with a straight-through estimator (`w_master + (w_served - w_master).detach()`), so the
data and the loss come from one policy and gradients land on the fp32 master. The fp32 arm
samples and trains on the master directly. Held-out accuracy is greedy decoding on the first
500 GSM8K test problems.

## Related work

- **Fair Cast** ("bf16 Rounding Silently Discards Most RL Policy Updates", arXiv 2610.41073):
  RTN bf16 export discards most per-step updates (0.4-0.5% of weights change per step on
  Qwen3-1.7B); exporting with stochastic rounding or error feedback and computing the loss on
  the served copy fixes it. quantlag ports the idea to CPU int8/int4.
- **QuRL** ("Efficient Reinforcement Learning with Quantized Rollout", arXiv 2602.13953):
  quantized actor for rollouts; identifies that weight changes between RL steps are too small
  for quantization to capture and mitigates it with invariant scaling, plus Adaptive Clipping
  Range against long-term collapse.
- Stochastic rounding for low-precision training (Gupta et al., 2015) and error feedback /
  sigma-delta style compensation for compressed updates (Seide et al., 2014; Karimireddy et
  al., 2019) are the two unbiased-in-the-long-run rounding rules used here.
- GRPO (Shao et al., DeepSeekMath, 2024) is the RL objective; GSM8K (Cobbe et al., 2021) the task.
